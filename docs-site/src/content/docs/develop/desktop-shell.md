`src-tauri` is the desktop shell: a thin Tauri 2 app around the core. It
holds no analysis. Its Cargo package is `stannum` (library
`stannum_lib`, edition 2021), and it depends on `stannum-core` by path.

| File | Holds |
| --- | --- |
| `src/main.rs` | Calls `stannum_lib::run()`. |
| `src/lib.rs` | The Tauri builder: plugins, shared state, setup, and the list of Tauri commands. |
| `src/analysis.rs` | `stannum_command`, the one command into the core, and `stream_log`. |
| `src/attach.rs` | The window's side of attach: `ui.*` requests to the interface and change notices. |
| `src/splash.rs` | The splash window shown while the main window loads. |
| `tauri.conf.json` | Windows, bundle and build settings. `tauri.windows.conf.json` overrides them on Windows. |
| `capabilities/default.json` | What the main window may call. |
| `icons/` | Generated by `pwsh scripts/update-icons.ps1`; don't edit by hand. |

## One command into the core

```rust
#[tauri::command]
pub async fn stannum_command(
    state: State<'_, SharedSession>,
    command: String,
    args: Option<serde_json::Value>,
) -> Result<Response, Error> {
    let session = state.0.clone();
    tauri::async_runtime::spawn_blocking(move || session.invoke(&command, args.unwrap_or_default()))
        .await
        .map_err(|e| Error::internal(e.to_string()))?
        .map(Response::new)
}
```

`SharedSession` wraps an `Arc<stannum_core::commands::Session>`, managed as
Tauri state. Every command runs on a blocking worker, so a long solve
never freezes the window, and the core's JSON text goes back as it is
(`Response::new`) without being parsed again. A failure reaches the window
as `{kind, message}`.

**Don't add a Tauri command for analysis.** Add a core command instead (see
[Add a command](/StannumRevival/develop/add-a-command/)), so the browser
tests, Python, run files and attach get it too. The shell's own commands
are only for things that need the window or the file system and have no
meaning to the core:

| Tauri command | What it does |
| --- | --- |
| `save_diagram`, `load_diagram`, `save_binary` | Write and read diagram files and exports. |
| `show_snap_layouts` | Opens the Windows 11 snap layouts flyout from the custom title bar. |
| `splash::app_ready` | The main window says it has rendered. |
| `attach::attach_ui_reply`, `attach::attach_status` | Answers to a script's `ui.*` commands, and whether attach is listening. |

The `dev_bridge` example answers `save_diagram` and `load_diagram` too, so
the browser smoke test behaves like the app. If you add a shell command
that the interface calls during normal use, give the bridge, or the test's
shim, an answer for it.

## Log streaming

`stannum_core::logbook::install()` runs first in `run()`, so every crate's
`log::` lines land in the core's ring buffer. `stream_log` polls it every
150 ms and emits new lines on the `stannum://log` event; `logStore.ts`
listens and shows them in the log dock.

## Attach

At setup the shell starts `stannum_core::attach` on the window's own
`Session`, so a Python script (`stannum.attach()`) and the person at the
window share one case. Core commands from a script run directly on the
session. The shell then emits `stannum://attach-changed` so the interface
can refresh what the script changed. Commands named `ui.*` are emitted to
the window as `stannum://attach-ui` and wait up to 10 seconds for
`attach_ui_reply`; `src/store/attachStore.ts` answers them. The ticket file
and protocol are described in `crates/stannum-core/src/attach.rs`.

## Windows and the splash

The main window starts hidden. `splash.html` (a second Vite entry) shows
the animated logo; when the interface calls `app_ready`, the splash
finishes its animation, closes and the main window is shown. On Windows
the main window has no system decorations and the app draws its own title
bar (`src/shell/WindowControls.tsx`); `tauri.windows.conf.json` holds the
difference.

## Permissions

`capabilities/default.json` grants the main window the window controls the
title bar needs, open and save dialogs, file reads and writes in the
Documents, Downloads and Desktop folders, opening web links, and the updater
with the restart it needs. A new plugin or a new kind of
file access needs a line there, or the call fails at run time with a
permission error rather than at build time.

## Updater

`tauri-plugin-updater` is only registered when the Tauri config has
`plugins.updater`, which release builds get from an overlay
(`scripts/release/updater-config.ps1`, passed with `--config`). Other builds
have no updater, and the `updates_enabled` command tells the frontend so.
`src/store/updateStore.ts` checks, downloads and restarts (with
`tauri-plugin-process`); `src/shell/UpdateBar.tsx` shows it. How releases are
signed and where `latest.json` comes from is in `docs/releasing.md`.

## Building on Linux

Tauri needs WebKitGTK. `scripts/ci/install-tauri-deps.ps1` installs the
packages CI uses. Tauri embeds `../dist` when it compiles, so build the
frontend first (`npm run build`), or create an empty `dist/` folder when you
only want `cargo clippy` or `cargo check`.
