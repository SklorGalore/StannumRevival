Each table on this page compares a Stannum result with a reference: another
tool's solution, a published paper, an independent calculation. A cell holds
the **largest difference** over everything compared for that case, with the
**limit** the test allows under it. A test over its limit fails, and a
failing test stops a pull request from merging.

The numbers aren't typed in. The reference tests write them as they run,
and the documentation workflow runs them again before every build of this
site, so they belong to the commit named here:

<VerificationSummary />

To run the same checks and rebuild the tables yourself:

```powershell
pwsh scripts/verify.ps1
```

It writes `docs-site/src/data/verification.json`, which these tables read.

## Power flow against MATPOWER 8.1

rs-power's numerical behaviour targets the **MATPOWER 8.1 legacy core**
(AC power/polar Newton and DC power flow, constant-power loads). Reference
results were generated with MATPOWER 8.1 at a $10^{-10}$ mismatch tolerance
and are checked in as fixtures, so the tests need no MATLAB, Octave or
MATPOWER installation.

Each case is solved with every AC method (Newton, fixed slope, both fast
decoupled forms and Auto) and with the DC model. The AC row shows the worst
of the five methods. The case9 variants cover reactive limits, slack
reassignment, generators sharing a bus, infinite and zero-width reactive
ranges, taps, phase shifts, shunts, offline equipment, parallel branches and
nonconsecutive bus numbers. With infeasible reactive limits MATPOWER and
every method report the AC case as infeasible, so only its DC row has
numbers.

<VerificationTable suite="matpower" />

## RAW import against MATPOWER 8.1's importer

Every numeric bus, generator, branch and DC line field Stannum imports is
compared with what MATPOWER 8.1's `psse2mpc` makes of the same file
(relative difference), then the imported case is solved and compared with
MATPOWER's AC and DC solutions of it. The files cover revision layouts 23 to
33, every transformer `CW`/`CZ` combination, partial winding statuses, DC
line control modes and three of MATPOWER's own RAW test files.

## Saved solutions

These cases were saved solved by PowerWorld Simulator, so each bus record
holds the voltage that tool found. Stannum opens the file and solves it as
the app does, with its default settings (reactive limits, remote regulation,
switched shunts and taps all on, 0.1 MVA tolerance), and the voltages are
compared bus by bus. The limits are what a planner would accept between two
tools on the same case, 0.001 p.u. at any bus and 0.05 degrees, set before
the measurement rather than fitted to it.

Both cases now agree with PowerWorld within 0.0005 p.u. at every bus. Two
fixes got them there:

- **Continuous switched shunts that reached a limit stayed there.** A
  continuous (MODSW 2) shunt that touched an end of its range early in the
  solve was fixed at that end for good, even when the voltage later fell
  back past its setpoint, and a second continuous shunt at the same bus
  didn't move at all. On Texas this left the Del Rio 115 kV shunts out and
  bus 3051 0.036 p.u. low. They now return to voltage control as
  generators do, and shunts at one bus share the control.
- **A line duplicating a transformer.** The Memphis file has a line and a
  transformer between buses 54 and 55, both circuit 2. PSS/E and PowerWorld
  keep one branch per circuit; Stannum counted both. The line is now taken
  out of service with an import warning.

You can make the same check on your own case: after an AC solve, **Compare
with the file** on the Power flow overview sets the voltages the file was
saved with beside Stannum's.

## Meshed VSC grids: the published model

The station model reproduces every converter in Tables II and III of
Beerten, Cole and Belmans (2012), *Generalized steady-state VSC MTDC model
for sequential AC/DC power flow algorithms*, from its system-bus values. The
inputs are the tables' own rounded values, so the limits allow a little more
than the tables' rounding. See [Meshed VSC
grids](/StannumRevival/manual/hvdc/vsc-grids/#verification).

<VerificationTable suite="vsc-paper" label="Converter" />

## Meshed VSC grids: MatACDC 1.0

On Stannum's own two-area case, with three asynchronous AC grids and two
meshed DC grids, the solver agrees with MatACDC 1.0 (J. Beerten, KU Leuven).
MatACDC itself is not in the repository, only its results on this case.
Where a converter reaches its limits the two differ by design: Stannum puts
the converter exactly on its limit, as the paper describes, and MatACDC
stops just inside it. In that run the grid that reaches no limit still
agrees, which is the third row.

<VerificationTable suite="matacdc" label="Run" />

## Contingency analysis

The linear screen's flows after each outage are compared with a DC power
flow solved without that branch. The AC-checked outages are compared with
the same outage made as a study edit and solved on its own. Both sides
solve to $10^{-6}$ MVA here, so the comparison shows the method, not the
solve tolerance. At a loose 2 MVA tolerance a line rated 16 MVA could read a
few percent apart between two solves that both converged.

## Transfer limits

Every distribution factor the transfer limit run reports is compared with
moving 100 MW from the source to the sink in two DC power flows, in the base
case (PTDF) and with each outage taken (OTDF).

## PV curves

The nose of each [PV curve](/StannumRevival/manual/pv-curves/) is compared
with an independent pseudo-arclength continuation power flow, which goes
round the nose instead of stepping up to it, and the sink bus voltages along
the curve with PYPOWER solves at the same transfers. Both are made by
`crates/stannum-core/scripts/pv_reference.py`, with generator reactive limits
off; Stannum's smallest step is 0.01 MW here.

<VerificationTable suite="pv" />

## QV curves

Each [QV curve](/StannumRevival/manual/qv-curves/) is compared with PYPOWER
solves of the same case with the same condenser added at the bus, at every
voltage on the 0.01 p.u. grid from 1.1 p.u. down to 0.3 p.u., and so is the
reactive power margin. The reference is made by
`crates/stannum-core/scripts/qv_reference.py`, with generator reactive
limits off.

<VerificationTable suite="qv" />

## Other checks

These run with every pull request but have no table here:

- Analytic Jacobians against finite differences.
- Nodal power balance of solved cases.
- Singular systems, invalid inputs and nonconvergence.
- The three RAW readers (power flow for revisions 23 to 35, topology for 35,
  and Records and Case diff for 33 and 35) count the same buses,
  generators, branches, switching devices and loads in every RAW fixture
  each one supports. Known gaps are listed in the test with their reason:
  Records and Case diff can't yet read a RAW 35 file with substation data,
  or bus records that leave out trailing fields.

## Time and size budgets

Every pull request builds a 12,000-bus [synthetic case](/StannumRevival/manual/synthetic-cases/)
and works through it with the commands the app sends: open, attach
coordinates, solve, the diagram, the map, topology, Records, pages of the
Power flow, Records and contingency tables sorted, searched and filtered in
the core, and an N-1 contingency run. Each command has a budget for how long it takes and how much
it sends back, and the test fails when one goes over, so a change that makes
large cases several times slower is caught before it merges. It also checks
that the app keeps answering while a solve runs. The run's summary on GitHub
shows the table.

```powershell
cargo test --release -p stannum-core --test budgets -- --ignored --nocapture
```

`STANNUM_BUDGET_BUSES` builds a different size; budgets grow in proportion
(an N-1 run, which solves an outage per branch and generator, by the size
to the power 1.5). A weekly workflow, also run on request, works through an
80,000-bus case the same way.
The same seed always builds the same case, so `STANNUM_BUDGET_CACHE` can name
a folder to keep it in and reuse; CI keeps one until the generator or the
solver changes.

## Interface

A browser smoke test drives the real interface in Chromium against the real
Rust core on every pull request: opening MATPOWER and RAW cases, solving,
sensitivities, studies, every module, side by side, the palette, the log, DC
lines and VSC grids. The screenshots in this documentation come from that test.

## Adding a check

A reference test makes a `stannum_verify::Check` for each quantity it
compares, passes it every difference, and calls `finish()`, which fails the
test when the largest difference is over the limit. When `STANNUM_VERIFY`
names a file, `finish()` also appends the result to it, which is how
`scripts/verify.ps1` collects the tables. A new suite needs a place in
`stannum_verify::SUITES` and a `<VerificationTable>` on this page. Add the
test to the list in `scripts/verify.ps1`.
